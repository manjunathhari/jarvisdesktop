## Strengths

- **The concurrency design is careful and documented where it is used.**
  - There is one lock order everywhere: node, then connection, for the fence; turn, then budget, then reservation, for money.
  - Every transition takes `FOR UPDATE` and checks the state again under the lock.
  - Budget steps commit on a sibling connection (R12-13), so a crash leaves a committed ACTIVE reservation and never makes a second Claude call. `reserve` re-reads the reservation under its own lock after waiting for the budget row.
- **The fence comes first, in the database.** Every gateway-facing function calls `gw.current_node` first, and `record_sent` refuses terminal items under the row lock. The gateway therefore can't send after an ack or supersede has committed. The DB half of P2-E13 is a real 1,000-run, three-actor race with a full audit-chain check (`test_comm_db.py:840`).
- **Per-device send isolation (fix round 1, I-1) is done properly.** Each link has its own queue and sender, and every send is bounded. The listener, fan-out, ticker and sweep only enqueue. `reap()` plus `_retrieve` leaves no pending or unretrieved tasks, and tests cover a stuck socket, a blocked heartbeat and shutdown.
- **The irreversible path fails closed.** It covers:
  - one receipt per execution key, taken before the task moves;
  - duplicate names or file IDs in a listing, which are malformed;
  - verification only by a fresh OK listing;
  - a verification timeout;
  - the transition going first, so a refused move leaves nothing verified.
- **Refusals are audited consistently** (R7-1, R11-1), and `audited_call_in_job` makes it structurally hard to roll back a refusal.
- **The 2^53 − 1 cap is pinned by a real test** (`test_resume_last_seq_beyond_two_to_the_53_is_refused`). `record_resume_out_of_range` takes `numeric` and rejects fractions and non-finite values.
- **The test map is honest about what it can't cover** (Plan B, live checks), and records RED evidence for each gap it filled.

## The owner's five areas

1. **2^53 − 1 resume maximum (no widening): holds for integers, with a float caveat.**
   - A signed integer above 2^53 − 1 can't be canonicalised. `verify` catches `IntegerDomainError` as a `ValueError` and returns False, so the gateway refuses the handshake once with `bad_signature`, opens no connection and sends no chunk. This is tested at `test_gateway_delivery.py:421`.
   - Nothing downstream widens: `p_last_seq numeric`; `positions` only uses values at or below the stored max.
   - **Gap (M-1):** integral float spellings get through, up to about 9.2e18, and are treated as `beyond_max`.
2. **Send-timeout and cleanup coverage: covered on the relay side, with gaps in the session's own sends.**
   - Covered and tested: every relay send is bounded, a link timeout closes `send_timeout`, and the stuck node doesn't delay the others (`:1104`). A `SendTimeout` raised directly in `_serve` is also handled.
   - **Gaps (I-2):** the `error` reply in the DB-error branch, and the handshake's `challenge` and `welcome` sends (M-4 and I-2(d)). None of these is tested.
3. **Disconnect-recording failures: partly handled.**
   - When `gw.close_connection` itself fails, the failure is logged, the socket still closes, and the next connect supersedes the row. This is tested on the send-timeout and heartbeat paths (`:1173` and `:1205`).
   - **Gap (I-2):** paths where `_db_close` is never attempted, such as a peer gone during a reply in `_serve`, or a welcome failure after `open_connection`.
4. **Queue cancellation and task shutdown: sound.**
   - `NodeLink.close` reaps the sender and drains the queue with `task_done`, so `idle()` can't hang. `_established` reaps all three tasks.
   - Queued work is only work, not state: it is recoverable from the DB after a restart (test at `:1314`), and the shutdown test shows nothing left pending and no unretrieved exception.
   - Minor: the caller's own cancellation is swallowed (M-5), and shutdown disconnects are recorded as `node_closed` (M-3).
5. **Cross-device acknowledgement isolation: holds in the database, with one leak in the gateway.**
   - `record_sent`, `record_received` and `acknowledge` all check the person and the target under `FOR UPDATE`. The relay's offer and clear filter by target. The sweep is per node (`d.received_at`), and `_acked_here` stops a clear going back to the acknowledging node.
   - **Leak (I-1):** the `welcome` summary.
   - **P2-E13 at 200 against 1,000 runs:** acceptable as a CI default. The real concurrency lives in the DB half, which runs 1,000 three-actor races. The gateway half applies its ops one after another from the test thread, so more runs mainly re-sample similar sequences (about 24 s for 200). But the count is the lesser problem: the node half asserts nothing about the gateway (I-3). Fix I-3, then add an optional 1,000-run mode (M-7).
